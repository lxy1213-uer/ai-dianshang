## 二、三条后续需求（事项卡）

> 共同约束：三条需求都沿用现有分层——「模型只负责理解与表达，规则与状态留在代码里」，新增能力必须带测试并保持 712 项回归不退化。

### 事项 A｜工单状态回写与退货闭环

| 项 | 内容 |
|---|---|
| 优先级 | high |
| 建议角色 | 后端 / 平台 |
| 现状 | 工单创建后状态固定为「已建单」，退款只做状态模拟，用户问「我的退货到哪一步」答不上来 |
| 目标 | 工单有可推进的生命周期，状态变更可追溯，Agent 能如实回答进度 |
| 依赖 | 无，可独立开工；状态枚举需与事项 B 共用 |
| 不在范围 | 真实支付网关、退款打款、财务对账 |

**范围**：状态枚举与迁移白名单 → 状态回写接口（含并发与幂等） → 审计时间线 → Agent 新增 `query_ticket_status` 工具 → 前端工单卡片显示进度条。

**验收标准（可测）**

1. 状态机 `CREATED → REVIEWING → APPROVED → RECEIVED → REFUNDED`，另有 `REJECTED` / `CLOSED` 终态；非法跃迁返回 409 且不落库。
2. 同一状态重复回写返回同一版本号、审计日志只记 1 条（复用现有幂等键思路）。
3. 两个并发请求回写不同状态时只有一个生效，另一个返回冲突，最终状态一致（用多线程/多进程压测验证）。
4. `GET /api/tickets/{id}` 返回当前状态、状态时间线、更新时间与下一步说明。
5. Agent 回答进度时只引用库里的真实状态与时间戳，不出现编造的金额、日期或预计到账时间。
6. 每次状态变更写 trace 事件（操作者、前后状态、时间）；重启后时间线不丢。
7. 新增 ≥ 6 项测试，`pytest -q` 全量通过；评测集 48 条不退化。

**拆分建议**：① 状态枚举与迁移表 → ② 接口与并发控制 → ③ Agent 工具与话术 → ④ 前端进度条。

### 事项 B｜人工坐席工作台（转人工闭环）

| 项 | 内容 |
|---|---|
| 优先级 | high |
| 建议角色 | 客服产品 + 前端 + 后端 |
| 现状 | `human` 意图只回一句「已转人工」，没有队列、没有接管、没有 SLA，转过去就断了 |
| 目标 | 转人工之后有人接、接得住、事后可追溯 |
| 依赖 | 事项 A 的工单状态（坐席需要看到工单当前状态） |
| 不在范围 | 真实 IM 通道、排班、绩效计费 |

**范围**：转人工入队（打包会话上下文） → 坐席列表/筛选/认领 → 坐席回复回写用户会话 → SLA 计时与超时标记 → 结束归档 → 坐席端页面。

**验收标准（可测）**

1. 转人工生成一条待办记录，包含最近 N 轮对话、`slots`、当前状态、政策引用、工单号；关键字段缺失率 0。
2. 坐席端可列表、筛选、认领；同一会话只能被一个坐席认领，重复认领返回冲突。
3. 坐席回复后用户在**原会话**里能看到该回复，且后续 Agent 消息不覆盖、不冲掉坐席消息。
4. 超过 SLA（建议 5 分钟未认领）自动打超时标记，可在列表中筛选。
5. 归档后会话仍可查询，trace 中有 `human_handoff` / `agent_takeover` / `resolved` 三类事件。
6. 越权：坐席不能查看非自己队列的会话，按 `user_id` 隔离做测试。
7. 新增 ≥ 5 项测试，并跑一次端到端演示：转人工 → 认领 → 回复 → 归档。

**拆分建议**：① 队列模型与接口 → ② 上下文打包（复用现有 trace/citations） → ③ 坐席端 UI → ④ SLA 与归档。

### 事项 C｜真实埋点与转化漏斗

**验收标准（可测）**

6. 埋点写入失败不影响主链路（异步或降级），聊天接口仍返回 200。
7. 用 48 条评测集回放，漏斗数字与评测结果一致。

**拆分建议**：① 事件字典（先定） → ② 落库与幂等 → ③ 聚合接口 → ④ 看板页 → ⑤ 脱敏断言。

## 四、执行顺序建议

1. **先定两份公共协议**：工单状态枚举（A 用）+ 事件字典（A/B/C 共用）——这两样定晚了会返工。
2. **A 工单状态回写**：纯后端，可独立验收，先拿到「退货到哪一步」这个最常被问的能力。
3. **B 人工坐席工作台**：依赖 A 的状态展示，补齐「机器办不了时有人接」的闭环。
4. **C 埋点漏斗**：A/B 上线后有真实流量才有意义，最后做。
